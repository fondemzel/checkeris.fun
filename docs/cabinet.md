# Кабинет checkeris.fun/cabinet

Табличный просмотр чеков из приложения «Проверка чеков» (ФНС): чеки, позиции внутри чеков,
фильтры, сортировка, экспорт в CSV, категории товаров с ручной правкой из карточки.

## Из чего состоит

| Путь | Что делает |
| --- | --- |
| `api/db/schema.sql` | Схема SQLite: `receipts`, `items`, представление `v_items`, журнал `imports` |
| `api/src/import.mjs` | Импорт выгрузок ФНС из `api/data/fns_out/*.json` в базу |
| `api/src/queries.mjs` | SQL-запросы кабинета: фильтры, сортировка, пагинация |
| `site/cabinet/icons.js` | Иконки групп категорий: контурный SVG, имя фигуры задаётся в `categories.json` |
| `api/src/server.mjs` | HTTP: JSON API + отдача статики из `site/` |
| `site/cabinet/` | Интерфейс кабинета (`index.html`, `app.js`, `styles.css`) |

Внешних зависимостей нет: SQLite берётся из встроенного модуля `node:sqlite`, сервер — из `node:http`.
Нужен **Node 22.5+** (проверено на 24.14). `npm install` не требуется.

## Запуск

```bash
node api/src/import.mjs      # залить выгрузки в api/data/checker.db
node api/src/server.mjs      # http://localhost:8787/cabinet
```

Переменные окружения: `PORT` (8787), `HOST` (127.0.0.1), `CHECKER_DB` (путь к базе),
`CHECKER_SITE` (каталог статики).

Импорт идемпотентен: чек опознаётся по тройке ФН/ФД/ФП, повторный запуск обновляет запись,
а не создаёт дубль. Позиции чека при обновлении перезаписываются целиком.

Из этого следует важное для следующего этапа: `receipts.id` стабилен между импортами,
а `items.id` — нет (позиции пересоздаются). Разметку по категориям нужно привязывать
к паре `receipt_id` + `pos` либо к нормализованному названию, но не к `items.id`.

## API

Все суммы — **в копейках** (целые), как приходят из ФНС. Форматирование — на клиенте.

| Эндпоинт | Ответ |
| --- | --- |
| `GET /api/meta` | Итоги по базе, список продавцов для фильтра, разбивка по месяцам, дата последнего импорта |
| `GET /api/receipts` | `{ rows, totals: { count, sum, items }, page, per, sort, dir }`; `kind=manual\|scan` — только вбитые руками или отсканированные |
| `GET /api/receipts/:id` | Чек с реквизитами и полным списком позиций |
| `DELETE /api/receipts/:id` | Удаление — только ручной записи |
| `POST /api/manual` | `{ sum, date, time?, name?, category }` — трата без чека, сумма в рублях |
| `POST /api/scan` | `{ qr }` — строка из QR чека в очередь к ФНС |
| `GET /api/scan?state=failed\|pending` | Сканы без чека и счётчики для фильтров; без `state` — и те и другие |
| `GET /api/scan/:id` · `POST /api/scan/:id/retry` · `DELETE /api/scan/:id` | Состояние скана; повтор и удаление — только у скана с ошибкой |
| `GET /api/items` | Позиции с контекстом чека, `totals: { count, sum, receipts }` |
| `GET /api/items/:id` | Позиция со всеми реквизитами — для карточки товара |
| `POST /api/items/:id/category` | `{ category: "<slug>" }` — ручная категория товара |
| `GET /api/summary?by=group\|category\|month\|seller` | Сводка: суммы в разрезе, с названиями, иконками и цветами. Фильтры те же, что у списков |
| `GET /api/taxonomy` | Справочник: группы, категории и на что каждая завязана |
| `POST\|PATCH\|DELETE /api/taxonomy/groups[/:slug]` | Правка групп; удалить можно только пустую |
| `POST\|PATCH\|DELETE /api/taxonomy/categories[/:slug]` | Правка категорий; удаление требует `?move_to=<slug>`, если на категорию что-то ссылается |
| `GET /api/export.csv?type=receipts\|items` | CSV для Excel: `;`, десятичная запятая, BOM. До 50 000 строк |
| `POST /api/auth/telegram/start` · `GET /api/auth/telegram/poll` | Вход через Telegram, см. «Доступ» |
| `POST /api/telegram/describe` · `POST /api/telegram/confirm` | Только для бота, с подписью |
| `GET /api/session` | Кто вошёл: имя, роль, привязан ли Telegram |
| `DELETE /api/account` | Удалить свой аккаунт со всеми данными (кроме администратора) |

### Доступ

Проверяет приложение, а не nginx: телефону нужен токен, который можно выдать и отозвать.
Токен живёт 90 дней и передаётся в `Authorization: Bearer`. Открыты наружу только вход,
`/api/version` (номер версии и «есть ли пользователи») и адреса для бота с проверкой подписи.

Пароль хранится хешем scrypt с солью, токен — хешем sha256: утечка базы не даёт войти.
Вёрстка кабинета открыта — данные закрыты, как в любом приложении.

**Вход через Telegram** — основной, он же регистрация: незнакомый Telegram получает новый
аккаунт (логин `tg:<id>`, пароль `!` — не совпадёт ни с одним) и копию системного справочника.

1. Браузер: `POST /api/auth/telegram/start` → одноразовый код (10 минут, в базе — хеш) и
   ссылка `t.me/checker_costs_bot?start=<код>`. Код берётся заранее, как только показан
   экран входа: Safari на iPhone не откроет Telegram из кода, выполненного после ожидания сети.
2. Бот (vps3, см. [deploy.md](deploy.md)) спрашивает `POST /api/telegram/describe` и показывает
   человеку, **с какого устройства** запрошен вход: «iPhone · Safari» — [Войти] [Это не я].
   Это защита от подмены: иначе можно начать вход у себя, прислать ссылку жертве,
   и её «Start» впустил бы в её аккаунт.
3. Нажатие — `POST /api/telegram/confirm` от бота; аккаунт находится или создаётся.
4. Браузер опрашивает `GET /api/auth/telegram/poll?nonce=` и получает токен — один раз.

Запросы бота подписаны: заголовки `X-Checker-Ts` и `X-Checker-Signature` =
HMAC-SHA256(`TG_RELAY_SECRET`, «время.тело»), расхождение времени — не больше 5 минут.
С токеном и `{ link: true }` начало входа — не вход, а **привязка** Telegram к вошедшему
аккаунту (кнопка «Привязать Telegram» в подвале кабинета).

**Пароль** остался для аккаунтов, заведённых до Telegram: `users.mjs --add | --password |
--tokens | --revoke`, новому сразу выдаётся копия системного справочника. Смена пароля отзывает
все выданные токены. Импорт выгрузок и ручных трат из консоли кладёт данные первому
пользователю, другому — с флагом `--user <логин>`.

**Роли.** `admin` — первый пользователь, владелец проекта: без квот, его аккаунт нельзя
удалить из приложения. Остальные — `user`.

**Квоты** ([quota.mjs](../api/src/quota.mjs)): лимит ФНС и модель общие на всех, поэтому у
каждого суточный предел — `USER_DAILY_SCANS` сканов (30) и `USER_DAILY_MODEL_NAMES`
незнакомых названий для модели (100). Кончилась квота модели — позиции остаются без
категории, человек выбирает её сам.

**Частота.** Вход паролем и начало входа через Telegram — не больше 20 запросов за 10 минут
с одного адреса (адрес — из `X-Real-IP`, который ставит nginx).

**Удаление аккаунта** — `DELETE /api/account`, в мобильной версии: значок аккаунта →
«Удалить аккаунт и все данные». Всё личное уходит каскадом внешних ключей одним запросом.
Что хранится и где — [site/privacy.html](../site/privacy.html).

### Пользователи и их данные

У каждой записи о деньгах есть владелец, и чужие записи не видны ни в одном ответе API.

| Личное (есть `user_id`) | Общее |
| --- | --- |
| чеки (`receipts`), их позиции и разметка (`item_labels`) | словарь названий (`dictionary`) |
| сканы (`scan_jobs`), ручные траты | штрихкоды (`gtin_map`) |
| справочник: `groups`, `categories` | правила продавцов (`seller_rules`) |
| ручные правки категорий (`user_dictionary`) | системный справочник (`sys_groups`, `sys_categories`) |
| связи с системным справочником (`category_links`) | |

Фильтр по владельцу ставит `buildFilters` в [queries.mjs](../api/src/queries.mjs), и без
владельца он бросает ошибку: забытое условие должно ронять запрос, а не показывать
чужие чеки. Чек уникален по ФН/ФД/ФП **в пределах владельца** — один и тот же чек
(общий ужин) могут отсканировать двое.

Тест изоляции (второй пользователь не видит и не трогает данные первого, чужие чеки,
позиции и сканы по прямой ссылке отвечают 404) прогонялся по всем маршрутам API
при переходе на эту схему.

### Справочник категорий: системный и личный

**Системный** (`sys_*`) — язык общего знания: словарь, штрихкоды и правила продавцов
пишутся в его кодах, модель размечает в них же. Он же — шаблон, который копируется
каждому новому пользователю. Правит его администратор из консоли:

| Команда | Что делает |
| --- | --- |
| `categories.mjs --show` | системный справочник и сколько на что ссылается |
| `categories.mjs --check` | проверить `categories.json`, ничего не меняя |
| `categories.mjs --export` | база → файл, чтобы закоммитить |
| `categories.mjs --sync` | файл → база |
| `categories.mjs --from-user <логин>` | личный справочник → системный: так правки в кабинете доходят до шаблона и модели |

**Личный** — копия системного при заведении пользователя (`provisionTaxonomy`). Дальше
человек переименовывает, перекрашивает, переносит, добавляет и удаляет что угодно в разделе
«Категории». Изменения шаблона получают только новые пользователи: сливать их поверх
чужих правок нельзя.

**Связи** (`category_links`) говорят, куда у этого человека ведёт каждая системная
категория. Сразу — в свою копию. Удалил «Доставку еды» с переносом в «Рестораны» —
связь переезжает туда же, и общее знание продолжает раскладывать доставку правильно.
Лестница разметки ([classify.mjs](../api/src/classify.mjs)): сначала личная правка,
затем общее знание в системных кодах, переведённое через связи. Нет связи — идём
по цепочке запасных (`sys_categories.fallback_slug`), нет и там — ступень не сработала.

Категории, созданные пользователем, ни с чем системным не связаны: туда ведут только
его ручные правки. Одобренная администратором пользовательская категория становится
системной с запасной — той, из которой выделилась; у остальных её товары идут туда же,
куда шли раньше (этап «предложить всем» ещё не сделан).

`slug` — идентификатор, а не адрес, и неизменен: переименование и перенос между группами
**не требуют переразметки**. Группу задаёт `group_slug`, а не префикс slug'а.

Ручные правки, сделанные до разделения, остались в общем словаре с `source = 'manual'`
как выверенное знание — новые пользователи получают эти названия размеченными.

`deploy_site.sh --db` заливает серверную базу целиком и затирает данные **всех**
пользователей; перед заливкой показывает, сколько пользователей и чеков пропадёт.

### Схлопывание одинаковых названий

Список товаров показывает одну строку на название: количество и сумма сложены, дата —
последняя покупка. Стрелка слева раскрывает покупки этого названия (до 200 строк, дальше
подпись «показаны первые N из M»). Клик по строке открывает карточку верхней позиции группы.

Схлопывает сервер (`listItemGroups`, `?collapse=1`), а не клиент: одинаковые названия
разбросаны по всей выборке, а список тянется порциями — половина строк ещё не загружена.
Пагинация в этом режиме идёт по названиям, поэтому `totals.count` — названия,
а число позиций за ними приходит в `totals.positions`.

### Ручные траты

`api/data/fns_out/manual_data.csv` — расходы, которых в чеках ФНС нет: аренда, кредиты,
налоги, наличные, переводы. Формат без заголовка: `название,сумма,количество,дата,,категория`.
Заливает `import_manual.mjs`, он же вызывается из `deploy_site.sh --data`.

Каждая строка становится чеком с одной позицией и продавцом «Ручная запись». Настоящих
ФН/ФД/ФП у неё нет, поэтому ключ идемпотентности — хеш содержимого строки: повторный
запуск обновляет записи, а не создаёт вторые.

Категория в файле проставлена человеком и **не выводится из названия** («Оля» — платёж
по кредиту, «Эмиль» — такси). Поэтому она пишется в `item_labels` с источником `pinned`,
а `classify.mjs --apply` такие позиции пропускает: пересчёт их бы не восстановил.
Строку с неразборчивой суммой или датой импорт не тащит в базу, а печатает целиком —
выгрузки из таблиц приносят то `#N/A`, то пустую ячейку.

С телефона ручная трата вбивается формой («+» → «Вбить вручную») и ложится так же:
чек с одной позицией и закреплённой категорией, только ключ у неё случайный. Удалить
можно любую ручную запись, но строка из файла вернётся при следующем импорте.

### Сканы, на которые ФНС отказала

Касса передаёт чек в ФНС с задержкой — от минут до суток и больше. Пока данных нет,
ФНС отвечает кодом **455** («Не найдены данные в сервисе поиска чека») или **544**
(«Не прошла проверка пара ККТ+ФН» — свежая регистрация кассы). Такой скан не хоронится:
очередь сама переспрашивает через 1 час, 6 часов, сутки и трое суток (`RETRY_HOURS`
в `scan.mjs`); все повторы одного скана стоят около десятка обращений из суточного
лимита. Прочие отказы — окончательные.

У ошибки непустой `next_at` значит «назначен повтор», поэтому окончательный отказ
обязан его обнулять. В мобильной версии такие сканы собраны в «Чеки → С ошибкой»:
там видно, когда будет повтор, и можно спросить сразу или удалить скан. Повторный скан
того же чека тоже запускает повтор.

### Что не попадает в суммы

Выгрузка ФНС содержит чеки, которые нельзя складывать напрямую, иначе итог завышается:

- **возврат прихода** (`operation_type = 2`) — не трата, а её отмена;
- **чек, закрытый зачётом аванса** (`prepaid_sum > 0`) — вторая половина предоплаченной
  покупки. Заказ выдаёт два чека: платёж (позиции с типом «платёж», деньги ушли картой)
  и отгрузку (те же товары, оплата — зачёт ранее внесённого аванса). Деньги списаны один раз.

Признак считается в `v_items.counted` и в выражении `COUNTED` в `queries.mjs` — одно правило
на оба списка. Такие строки остаются видимыми и помечены значком, но в `totals.sum` не входят;
их сумма отдаётся отдельно как `totals.excluded_sum`. На базе автора это 174 чека и 338 737 ₽ —
8 % итога.

### Ручная правка категории

Выбор категории в карточке товара меняет категорию не одной позиции, а всех позиций
**этого пользователя** с таким же нормализованным названием: он решает, что такое
«Сыр Российский 45 %», а не что такое конкретная строка чека. Запись идёт в его
`user_dictionary` — верхнюю ступень его лестницы в `classify.mjs`, выше GTIN и правил
продавца; на других пользователей правка не влияет, общий словарь не меняется.
Метки одноимённых позиций обновляются тем же запросом, чтобы список не ждал пересчёта.
Пустой slug снимает ручное решение, и эти позиции сразу заново проходят лестницу.

Общие параметры фильтрации: `q` (поиск по названию позиции, продавцу, точке; для чеков —
ещё и по позициям внутри чека), `from`, `to` (даты `YYYY-MM-DD`), `seller_inn`, `operation`
(1 приход, 2 возврат), `min_sum`, `max_sum` (в рублях), `page`, `per` (≤ 500),
`sort` + `dir` (`asc`/`desc`).

Сортировки: чеки — `date`, `sum`, `seller`, `place`, `items`; позиции — `date`, `name`, `sum`,
`price`, `quantity`, `seller`. Значения вне белого списка молча заменяются на `date`,
пользовательский ввод в SQL уходит только параметрами.

## Особенности данных ФНС

- Суммы в копейках, `quantity` почти всегда `1`, `unit` заполнен у единиц позиций.
- Строки приходят с хвостовыми пробелами (`userInn`, `kktRegId`) — импорт их обрезает.
- В выгрузке встречаются дубли одного чека под разными `_id`: в исходном файле за 2025 год
  1351 запись, уникальных чеков 1346.
- Ставка НДС в позиции — код ФФД: 1 = 20%, 2 = 10%, 3 = 20/120, 4 = 10/110, 5 = 0%, 6 = без НДС.
  Суммы по расчётным ставкам (`nds18118`, `nds10110`) сложены с соответствующими процентными.
- `retailPlace` для интернет-магазинов содержит домен (`ozon.ru`), у чека стоит `internetSign`.
- Названия позиций обрезаны кассой (≈40 символов) и написаны как попало — это главная сложность
  для будущей категоризации. Для поиска в `items.name_norm` лежит нормализованный вариант
  (нижний регистр, `ё`→`е`, схлопнутые пробелы).
- Исходный `receipt` целиком сохраняется в `receipts.raw` — чтобы можно было пересобрать
  производные поля, не перечитывая выгрузки.

## Интерфейс

Три зоны: слева тёмное меню разделов, в центре список, справа карточка выбранной строки.

- Разделы **Чеки** и **Товары** — пункты бокового меню. В шапке раздела заголовок, поиск
  и экспорт; под ней два ряда чипсов: период (Все / День / Неделя / Месяц / Год плюс
  произвольный диапазон дат) и сумма (Все / до 100 / 1 000 / 5 000 / 10 000 / 50 000 / 100 000 ₽).
- Пресеты периода считаются от сегодняшнего дня: «Неделя» — последние 7 дней, «Год» — 365.
  Правка дат вручную снимает пресет. Чипсы суммы задают верхнюю границу: для чеков —
  итог чека, для товаров — сумму позиции.
- Список подгружается порциями по 100 строк при прокрутке, страниц и переключателя
  размера страницы нет. Если порция не заполнила панель целиком, следующая тянется сразу.
  В подвале видно «показано N из M».
- В списке только четыре колонки: дата, название, количество, сумма. Всё остальное
  (ИНН, адрес точки, оплата, НДС, ФН/ФД/ФП, смена, кассир, GTIN, поставщик) — в карточке справа.
- Карточка чека содержит список позиций; клик по позиции открывает карточку товара,
  из карточки товара кнопка возвращает к чеку.
- Состояние (фильтры, сортировка, страница, выбранная карточка) живёт в query-параметрах,
  ссылкой можно поделиться: `/cabinet?view=items&q=молоко&sort=sum`. Выбранная карточка —
  параметр `card`: `r<id>` для чека, `i<id>` для позиции.
- Кнопка «Экспорт CSV» выгружает текущую выборку с учётом всех фильтров.
- Ниже 1100px панели складываются в одну колонку: карточка уходит под список.
- Новый раздел добавляется пунктом `.nav-item` в меню и веткой в `COLUMNS` — заголовок,
  фильтры и карточка переиспользуются.

## Деплой

Сервер отдаёт и статику, и API, поэтому за nginx достаточно проксировать домен целиком:

```nginx
location / {
    proxy_pass http://127.0.0.1:8787;
}
```

Либо отдавать `site/` напрямую nginx, а на Node проксировать только `/api/`.

Кабинет закрыт от индексации (`<meta name="robots" content="noindex">`), но **не защищён
авторизацией** — пока данные лежат в одной общей базе, это внутренний инструмент. Аутентификацию
и разделение по пользователям имеет смысл делать вместе с личными кабинетами.
